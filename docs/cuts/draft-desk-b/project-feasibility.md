# 路②/③ 项目内可行性深挖（配 tech-recon.md + research-pagination-engines.md）

- 日期：2026-07-12
- 用途：刀B parity 方向拍板的项目内事实证据。只读调研，未改代码。

## 0. Vivliostyle 到底用在哪（grep 核实，回答「换引擎波及面」）

Vivliostyle **只出现在导出 PDF 路径**，与「解析面板」零关系：
- `server/print-renderer.mjs`：生成给 Vivliostyle 的 HTML+CSS（也同时供浏览器打印）。
- `server/draft-paper/draftPaperStore.mjs:830-899` `exportDraftPaperPdf`：**草稿卷 PDF 导出（活路径，刀B 正主）**。
- `server/exports/exportImplementation.mjs:129` `renderPrintPdfWithVivliostyle`：**旧 paperAssembly PDF 导出（孤儿路由，UI 不可达，刀B 可不动）**。
- `server/exports/exportRoutes.mjs:52` + `app/src/services/questionGroups.ts:521-527`：vivliostyle 缺失→503 错误映射/前端提示。
- `server/package.json` `@vivliostyle/cli@^9`；scripts/* 测试与 QA。

「解析面板」= 纯 React 屏幕组件（`app/src/features/reading-analysis/*`、`paper-intelligence/*AnalysisPanel.tsx`、
`question-detail/AnalysisDisclosure.tsx`），**不引用 Vivliostyle**。屏幕解析显示与出 PDF 的引擎是两回事——
换分页引擎动不到解析面板。

## 1. print-renderer.mjs CSS Paged Media 特性（逐条）

- `@page` A4 + `margin:21mm 24mm 24mm 24mm`（456-458）。
- `@bottom-center` 页脚用 `counter(page)`+`counter(pages)`（460-467）；草稿卷经 `draftPaperStore.mjs:196-208`
  `addDraftFooterCss` 级联覆盖成「标题 · 页码」（无总页数）。
- **显式强制分页已存在**：`.page-break{break-before:page}`（507-509）。
- `break-inside:avoid`：`.question`（题干+选项整体）、`.writing-answer-box`、`.print-figure*`（616-628/552/567）。
- `break-after:avoid`：`.section-header,.group-meta,.group-header`（620-624）。
- **`orphans`/`widows` 全文零使用**；无 running header。
- **`.passage`/`.passage p` 无 break 规则（534-542）——不是疏漏，是产品标准**：
  `exam-paper-format-standards.md` §3b「篇章段落可以跨页，不做题组原子化、不留整页空白」（owner 2026-07-08 拍板）。
  **即：打印「段落可跨页」是 owner 认证的正确行为；屏幕预览「passage 当整块」才是要修的缺陷。**

## 2. 显式断点管道（已在生产跑通）

`buildPrintHtml` 的 `blocks` 数组本就支持 `{type:'page_break'}`→`.page-break`；
`draftPaperStore.mjs:153-176 buildDraftPaperBlocks` 第 160 行已把 `item.pageBreakBefore` 喂给 Vivliostyle。
**但只有「题组边界」粒度**（`draft_paper_items` 一行=一题组，`page_break_before` 是列）；`decisions.md:128-129`
「Page breaks must never split inside a group」限定的是人工/建议插入粒度。要表达题组**内部**断点，
`print-renderer.mjs` 目前对 `.question`/`.passage`/`.group-header` **无可寻址标记**，需新增。

## 3. 预览分页结果 = 纯 DOM 副作用（三个精度陷阱）

`paginateA4Preview` 重排 DOM，节点带 `data-group-id`，但今天只被数了 `.preview-page` 个数
（`DraftPaperWorkbench.tsx:293-299`），无人提取「每页装哪些 groupId」。提取本身几十行，但有陷阱：
- **陷阱1（box-model 不同步）**：预览内容区 = 257mm×174mm（padding 20/18mm），打印 = 252mm×162mm
  （margin 21/24mm）。**预览可用宽度比打印宽 ~7.4%**，两组数字各自手写从未同步。即便拿到干净断点，
  也是在更宽画布上量的，搬到 Vivliostyle 窄画布会被迫再次溢出→页数对不上。**路②任何变体都要先同步 padding**。
- **陷阱2（长 passage 无断点可喂）**：`flatten()` 不递归拆 `.passage` 的 `<p>`，超长原文只让页撑高、不产断点。
  解药 = `flatten()` 递归拆到 `<p>` 级 = **路①的核心动作**。**⇒ 不管选路①还是路②/③，这一刀都逃不掉。**
- **陷阱3（字体度量差）**：服务端渲染实际字形 = Liberation Serif/Noto CJK（生产已装），≠ 教师本机
  真 Songti/Times，临界行数可能卡线。量级小于陷阱1，记录备查。

## 4. Playwright/Chromium 现状（利好，且揭示关键事实）

- `app/package.json` 有 `playwright@^1.60`（devDep，QA 用）；**`@vivliostyle/cli` 内部依赖 `playwright-core`
  跑无头 Chromium**——**今天的 PDF 导出骨子里已经是 Playwright 驱动的 Chromium**，A2/A3 用 Playwright
  不是引入新栈，是把被 Vivliostyle CLI 包住的同一引擎换直接调用。**这条件同样支撑 paged.js（pagedjs-cli 底层也封 Puppeteer/Chromium）。**
- 生产无头 Chromium 基建已踩坑修平（`go-live-record.md:79-144`：系统库 + 字体映射）。
- 若在导出同步路径直接调 Playwright，需把 `playwright-core` 提为 `server` 正式依赖（明确可控的一步）。

## 5. A1/A2/A3 结论

- **A1-浅（题组边界断点喂 Vivliostyle）**：工作量**小**，复用现成 `.page-break` 管道，**在覆盖范围内既
  parity 又保真**（Vivliostyle 页内精排全保留）。但**解决不了最痛的长 passage 场景**（无断点可喂），
  也不解决题组内部断点差异；受陷阱1/3 影响。
- **A1-深（题组内部粒度）**：要给元素加寻址标记 + 客户端/服务端 flatten 顺序持续同步 + 先做 flatten 拆 passage
  + 触碰 decisions:128-129 约束。工作量**中-大**。
- **A2（Playwright 把预览 DOM 直接打 PDF）**：**结构上代价最小、最可靠**——渲染的就是预览已量好的 DOM，
  不存在「两套引擎各量各的」，box-model/题组粒度问题**根本不存在**。放弃 Vivliostyle 的 `@page`/计数器，
  换 Chromium 原生打印（`browserPrint()` 今天已在用同引擎）。**关键：`decisions.md:162-164` 原始拍板就是
  「PDF is generated by browser rendering / print-to-PDF from the draft preview surface, not by hand-building
  a second PDF layout engine」——A2 是把实现修正回 C8 最初批准的方向，Vivliostyle 才是后来偏离的分支。
  风险定性应下调。** 要新写：一层打印态 CSS（`.preview-page`→Chromium 原生分页边界）+ 服务端 Playwright
  链路 + 长文撑破兜底。安全注意：服务端应自己重渲 `buildA4PreviewHtml`，勿执行客户端提交的 HTML/JS。
- **A3（服务端复现测量）**：不是独立选项，是给 A1/A2 断点「消毒」（信任服务端一次测量而非教师本机）。
  接 A2≈零增量；接 A1 要多担 TS→shared 代码迁移，且去不掉陷阱1/粒度硬伤。

**逃不掉的第三个决定**：`flatten()` 递归拆 passage 到 `<p>` 级，是路①/②/③所有变体的共同前置修复，
独立于「选哪条路」，务必单列摆给 owner——不管选哪条，这一刀都要挨。
