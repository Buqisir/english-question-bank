# main 按累计改动选检查（提案，待审）

## 要解决的问题

主干开发后，main 上每次 push 都跑 Full（`verify.yml` 里 `pull_request` 以外一律 `--pack all`），哪怕只改一个按钮。实测：

| 情况 | 耗时 |
| --- | --- |
| main Full | 18.7–26.7 分钟 |
| PR 上 feature 包（#723） | 9.6 分钟 |
| 固定 6 项浏览器 seams（每次必跑） | 6.6–9.4 分钟，是当前结构下限 |

估计改界面、改文案的 push 可从约 20 分钟降到约 10 分钟。

## 为什么不能只看「这次 push 改了什么」

部署只看最新 main SHA 的一次运行。例：

- A：Full 全绿，已上线
- B：改服务器代码，检查红了（或只跑了小包）
- C：改一个按钮，只跑 UI 包，绿

部署 C 会把 B 一起带上线，而 C 的运行没测服务器。所以 main 不能按「相对父提交」选包。

也不采用「从线上到目标每个提交都必须全绿」：一次 push 多个提交时中间提交没有运行；子提交修好父提交后父提交永远是红的，部署会被永久卡住。

## 方案

main push 的选包改为：**以最近一个 Full 全绿的 main 祖先为基线，按「基线 → 本 SHA」的累计改动选包，在本 SHA 的完整代码上跑。**

上例中 C 的累计改动 = B 的服务器 + C 的按钮，所以 C 会跑到服务器相关检查。若 A 之后只改过界面，就只跑 UI/feature 包。

具体规则：

1. **基线 = 最近的 main 祖先 SHA，满足：** 它自己的 natural push 运行最新 attempt 全部 8 个 job 成功，且该运行实际执行的包是 `all`。运行的包要能从运行记录里读出来（例如每个运行上传一份选包结果 artifact）；读不出来的不算基线。「8 个 job 绿」本身不能证明跑过 Full。
2. **选包代码来自基线，不来自候选。** 和 PR 一样，用基线 SHA 的 `scripts/ci-pr-plan.mjs` / `verify-ci.mjs` 对 `git diff 基线 本SHA` 分类。候选改了分类器本身时，基线的分类器会把工具链路径判成 Full。
3. **main 上没有 PR 描述里的 risk-plan 建议**，直接采用基线分类器结果；分类器判高风险、paper、shared、unknown、工具链或任何失败，一律 Full。
4. **找不到可信基线就 Full**（查询失败、超出回看范围、基线不是本 SHA 祖先等）。
5. **部署读取器不改**：仍只认最新 main SHA 的 v4 8 job 全绿。安全性来自第 1–4 条：最新 SHA 的运行覆盖了「最近 Full 全绿版本 → 它」的全部改动，而最近 Full 全绿版本覆盖了它之前的全部。
6. 8 个 job 名、分片、PR 选包逻辑、分支保护都不变。

几种情况怎么走：

| 情况 | 结果 |
| --- | --- |
| 上次 Full 还没跑完就又 push | 基线退回更早的 Full 全绿版本，累计改动变大，必要时跑 Full |
| main 红了，下一个 push 修好 | 累计改动含红的那次，在修好后的代码上一起测；绿了就能部署 |
| 一直只改界面 | 基线不前进，但累计改动仍只是界面，持续跑小包 |
| 一次改到高风险路径 | 这次跑 Full，成为新基线 |

## 改动面（粗估）

6–9 个文件、300–600 行：`verify.yml` 选包步骤（6 个 worker 共用）、`ci-pr-plan.mjs` 增加 main 入口和基线查找、选包结果 artifact、对应测试、`AGENTS.md` CI 段和 `.agents/ship.md` 的描述。属于 CI 工具链改动：走 PR + 独立审查 + PR CI，不直推。

## 非目标

不改 PR 选包；不改 job 名和部署读取器；不部署旧 SHA；不加定时 Full 或新的验证层。
