# EQB Trunk-Based 定稿（V4 收敛版 · 终审修订）

2026-11-16 · 主会话与 Astra 共同敲定 · 同日终审修订（改动和依据见第六节）· 基线 main 2e70fb0f4

**目标：** 推得快，修得快，长期不靠 Owner 盯着。
**一句话：** 默认直接推 main，main 跑完整 CI，全绿后自动部署。PR 只留给三种情况：推不了 main 的会话、改 CI 和部署工具链、自愿讨论。

## 一、日常规则（激活后）

1. **什么时候推：** 任务 Goal 默认包含直推 main 和上线，不用 Owner 再说一次 Ship。Owner 说「先别推」或「先别上」才停。
2. **切小块：** 一个能说清、能验证的改动对应一个提交，几小时内做完。
3. **推前自检（L1）：** 先同步 `origin/main`，再看一眼 main 最近一次跑完的运行：是红的，就只能推修复或撤销（第二节）。然后按改动选现有命令，不新建清单：
   - 前端 / UI：`node scripts/verify-ci.mjs --pack ui`（构建、类型检查，以及 motion、radius、emoji 等守卫）
   - 工作台组件：再加 `node scripts/verify-similar-workbench-swap.mjs`（裸 fetch 守卫）
   - 其他：`node scripts/verify-ci.mjs --changed --base-ref origin/main`（必须显式写基线）。先加 `--plan-json` 看选出哪一档；选出 `all` 时不在本地跑 Full，只跑直接受影响的脚本，Full 交给 main CI
   - 统一：`git diff --check origin/main...HEAD`，并实际操作一次受影响的行为
   - 高风险（鉴权、答案隔离、持久化、题号和答案对应、准入、共享 Paper 契约）：另加一次独立审查（Astra），审查结论绑定候选 SHA，但不开 PR
   - **CI 和部署工具链**（`.github/workflows/`、`scripts/verify-ci.mjs`、`scripts/ci-pr-plan.mjs`、部署脚本和控制器）：继续走 PR，PR 完整 CI 绿、Astra 审过再合。这类改动改的是裁判本身，推上 main 以后它自己那次绿灯证明不了它没被改松
4. **直推：** `git push origin HEAD:refs/heads/main`。被拒绝就重新同步、重新自检后再推。永不强推。
5. **main 完整 CI：** 每次推送单独排队，按 SHA 分并发组，互不替换。
6. **推的人盯到出结果：** 推完任务还没完，要等自己那个 SHA 的运行跑完（中位 26 分钟）。main 的 CI 结果不会自己叫醒会话，要主动回查。会话等不了，就在 Linear 写明「SHA 待确认」，交给下一条的开工检查。
7. **自动上线：** 在 Owner「部署最新版」的长期授权下，最新 main 的 8 个 job 全绿后，Agent 自动部署并做线上验证；main 又前进了就重新解析，不用旧绿灯放行新版本。几条边界：
   - 部署只能在 Owner Mac 上做（私钥在钥匙串里）。不在 Owner Mac 上的会话部署不了，在 Linear 写「已绿待部署」。
   - 改了持久化路径（`data/sql`、`server/api.mjs` 等 11 处）或主机配置的版本，普通部署会被服务器上的控制器拒绝，要 Owner 单独授权。Agent 不绕，在 Linear 点名 Owner，写清哪次提交、哪些路径。它没部署之前，后面的提交也都上不了线。
   - 连续推送时最新 main 可能一直在跑，上不了线。要上线就停推一轮。
   - 可见改动上线后在线上做 Owner QA。现在没有外部用户，可以这样；有了真实老师再和功能开关一起重看。
8. **开工先看两眼：** 每个 Agent 开工先查：main 最近一次跑完的运行是不是绿；在 Owner Mac 上的再查线上是不是最新的绿版本。红了没人管就接手，绿了没部署就补部署。这是推的人不在时的兜底，不新增服务。
9. **更新 Linear：** 写 commit 链接、做了什么、验证情况、是否已上线。

**PR 路径（可选）：** 推不了 main 的会话（比如只能推自己分支的云端会话）开 PR，等 PR 的完整 CI 绿了再 squash 合并，不要求分支是最新的。合并后和直推一样，照第 6 条盯 main。

## 二、红灯与不稳定测试

- **谁推红谁负责。** 「谁」指第一个变红的 SHA 的推送者，之后叠上去的提交不算。从发现失败起 30 分钟内推出修复或撤销（不是 30 分钟内变绿，CI 本身要 26 分钟）。撤销前先看后续提交有没有依赖它、有没有数据兼容影响；有依赖就先评估再动，不机械撤销。撤销也是一次普通直推。
- **推的人不在：** 谁先发现谁接手（第一节第 8 条）。
- **红灯期间暂停普通推送**，只允许修复或撤销。
- **不稳定测试：** 失败的测试不在本次改动影响范围内，而且是已登记的不稳定签名时，允许整个 workflow 重跑一次，并记录下来。不只重跑失败的 job：部署脚本要求 8 个 job 都属于最新一次尝试，只重跑一个能不能过没有实测过，整个重跑是保险做法。第二次还失败，就按真问题处理。
- 已登记的不稳定测试（登记表放在 `docs/agents/testing-cadence.md`，不另建文件）：`e2e-seams-2`「persistent overlay button clusters render in A3 mode」（iframe 重载期间的竞态，近期出现 3 次）。

## 三、修得快：从修好到上线

| 环节 | 现在 | 直推后 | 提速后 |
| --- | --- | --- | --- |
| PR CI（含「分支要最新」引起的重跑） | 约 26 分钟 ×1–3 次 | 没有了 | 没有了 |
| main CI | 中位 26 分钟（21–34） | 同左 | 约 23 分钟（估算） |
| 部署 | 几分钟 | 几分钟，main 变绿后自动部署 | 同左 |
| 合计 | 1–2 小时 | 约 30 分钟，慢的时候 40 | 约 27 分钟 |

main CI 的数是 2026-11-13 到 11-16 的 12 次 main 运行实测。总时长由最慢的 job 决定，12 次里 11 次是 verify-1（中位 26.2 分钟），1 次是 verify-2（中位 20.6）。render-1 中位 15.8，从来不是最慢的。

提速先做两件最便宜的事：
1. **把两个 verify 分片分匀**（`scripts/lib/verificationShards.mjs` 的平衡覆盖，不改 job 集合）。分匀后两片各约 23 分钟，省 3 分钟左右。先从 job 日志里看 verify-1 哪几个脚本最慢再挪；它自己的耗时在 19–34 分钟之间摆动，摆动的原因也要一起看。
2. **修掉上面那个 A3 不稳定测试。** 按代码推断的原因：切 A3 以后卷面还会再排一次，旧的题组工具条先通过了「已挂上」检查，随后被重排卸掉，计数成了 0。修法是把 #721 加的「等切换后那一版落地」提到这条断言之前。没有复现验证过。

render 两片分匀不省总时长，不做。降到 20 分钟以内要加第三个 verify 分片，那会改 8 个 job 的集合和部署读取器，属于高风险，见第四节。每周用 `gh run list` 统计一次「推送到上线」的耗时。

## 四、这轮不做

- **功能开关（PostHog）：** 现在没有外部用户。等第一次需要对真实老师隐藏一个没做完的功能时再接。
- **固定提速指标、仪表盘、merge queue、新常驻服务、新签名体系。**
- **第三个 verify 分片、部署「不是最新但已全绿」的版本：** 都要改部署读取器的放行规则，属于高风险。先看分匀后的数据。
- **回滚时跳过 CI**（撤销到已验证过的同一版本就直接部署）：同样要改放行规则。等有真实用户再评估。

## 五、切换（两步）

**第 1 步：最后一个强制 PR。** 它属于工具链高风险改动，需要 Astra 审查，并跑完整 Full 和 E2E。改 4 个文件：
- `AGENTS.md`：Ship、推前验证、CI authority 三段（required checks、PR body、strict、watcher 相关表述）；**另加 Goal authorization 和 Owner Mac deployment 两段**，现在写的是「一次指令授权一次部署」「合并不代表部署」，长期授权和它的边界（只限普通代码部署，不含持久化和主机配置）要写进去，并写明 Owner 说「停自动部署」即停
- `.agents/ship.md`：默认路线改成直推加 main 收尾；开头「不授权部署」那句同步改；PR 风险块和 watcher 移到可选 PR 路径
- `.github/workflows/verify.yml`：main 的并发组改按 SHA 分组
- `docs/agents/testing-cadence.md`：写明推前 L1 和不稳定测试登记表，删掉强制 PR→main 两轮门禁

另外同步更新 `~/.factory/AGENTS.md` 里「开完 PR 更新 Linear」一条，改成「推 main 后更新 Linear」。

部署读取器、`ci-pr-plan.mjs`、watcher 不改，现有测试也不用改。

**第 2 步：激活。** 这一步需要 Owner 授权，因为要改 GitHub 设置：
- 先读一次 main 的保护设置，确认没有「必须经 PR 评审」那一项；有的话直推照样被拒，要一并处理
- 只删除 main 的 required_status_checks
- 保留 enforce_admins、线性历史、禁止强推、禁止删除分支
- 用现有个人凭据推送，不用 Actions 的 GITHUB_TOKEN（否则不会触发 CI）

然后用一个真实小修复走一遍：直推 → main CI 绿 → 自动部署 → 线上验证。

**完成标准：** 能正常直推；连续推送时每个 SHA 都有自己的完整运行；红灯或证据不全的版本部署不了；下一个 Agent 能从 Linear 接手。

**试行两周（数字是提案，Owner 可改）：** 每周记三个数：推送到上线的中位耗时；main 红了几次、每次红多久；撤销几次。两周里不稳定测试以外的红灯达到 4 次，或有一次红灯超过 2 小时没人处理，就复盘，先把出事的那一类改动挪回 PR 路径，不整体撤回。

**撤回办法：** 恢复 required_status_checks，即回到现在的 PR 路线。

## 六、终审修订记录（2026-11-16）

结论：方向同意，可以执行。直推加「部署只认全绿的最新 main」这个组合成立：main 可以短暂变红，线上不会跟着坏。下面是对照仓库和 CI 记录核实后改的地方。

| 改了什么 | 依据 |
| --- | --- |
| 提速第 1 件从「分匀 render」改成「分匀 verify」；main CI 从「约 25」改成中位 26；「提速后 15–20」改成约 23 | 12 次 main 运行逐个 job 量过：最慢的 11 次是 verify-1，render-1 一次都不是。原稿说的「render-1 25.5 分钟」在这 12 次里没出现（最大 20.6） |
| 加「推的人盯到出结果」和「开工先看两眼」 | main 的 CI 结果不会叫醒会话。今天 #721 合并后 main 红了，是 Owner 先发现的，之后靠定时回查才盯到绿。没有这两条，「谁推红谁负责」落不了地 |
| 自动上线加三条边界 | 部署走 Owner Mac 的钥匙串（AGENTS.md）；控制器遇到持久化路径改动报 `SEPARATE_MUTATION_AUTHORIZATION_REQUIRED`（`deploy/eqb-deploy-controller.mjs`），最近一周 46 次提交里有 4 次碰到这些路径；读取器只认最新 main |
| 第 1 步多改 AGENTS.md 两段和 ship.md 开头 | 这三处现在明文写着部署要 Owner 当次指令，不改就和长期授权矛盾 |
| CI 和部署工具链留在 PR 路径 | 最近一个月 211 次提交里有 22 次碰到这些文件，约一成。这一成多等一轮 CI（26 分钟），换来的是「裁判不自己给自己判」。这条是终审加的取舍，Owner 觉得太慢可以改回直推加审查 |
| PR 路径写明给推不了 main 的会话用 | 云端会话只能推自己的分支，本次终审所在的会话就是 |
| 红灯责任写明「第一个变红的 SHA」、30 分钟指推出修复 | CI 要 26 分钟，这段时间里叠上去的提交会跟着红，原稿没说算谁的 |
| `--changed` 选出 Full 时不在本地跑 | 本地 Full 不分片，会比 CI 还慢，和「推得快」相反 |
| 激活前先读保护设置；加两周试行和复盘条件 | 保护设置这次没能读到，不能假定；原稿只有整体撤回，没有中间档 |

没改、但要 Owner 明确点头的两件：一是「部署最新版」从一次一授权变成长期授权；二是第 2 步删除 required_status_checks。

没核实的：「现在合计 1–2 小时」这个数；main 的保护设置；只重跑失败 job 能不能过部署读取器。
